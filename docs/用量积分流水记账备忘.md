# 用量/积分流水记账备忘

> v2.5.0 新增：双流水统计（token 口径 + 积分口径），锦上添花功能，不触碰主链路。
> 决议来源：R17（分口径、不强关联、不折算）、R18（临期阈值可配）。

## 1. 设计决议

| 决议 | 内容 |
|------|------|
| 双口径独立 | token 流水（渠道×模型）与积分流水（账号 earn/spend/expire）各记各账，**不做积分↔token 折算**（无可靠基准价，宁缺毋滥） |
| 写入侧零开销 | 掉 API 时仅 append 一行到带缓冲句柄（8KB bufio），30s AutoFlush + UI 读取前 Flush；常驻内存 ≈ 8KB |
| 读取侧按需 | 仅 Web UI 请求 `GET /api/usage?days=` 时按月分段扫描聚合，边扫边聚合不保留原始行 |
| 文件有界 | 按月分段 `data/ledger/usage-YYYYMM.jsonl` / `credit-YYYYMM.jsonl`，启动清理 6 个月前的分段；重度使用 ≈ 1.5MB/月 |
| 成功口径 | 只记成功请求（含 usage 缺失但请求成功的情况，src=none）；失败/透传错误不计 |
| 零 token 红线 | 流水只含 uid/模型名/token 数量，绝无 access/refresh token（§6-2） |

## 2. token 流水（usage-ledger）

- **记录点**：`server/handler.go` chatCompletions 成功分支（流式 + 非流式两处）。
- **usage 来源**：`Upstream.Stream` 签名改为返回 `(map[string]any, error)`——末帧捕获的
  OpenAI 形状 usage；上游未返回时为 nil（记 0 token + 1 请求数）。
- **捕获实现**（按渠道）：
  - workbuddy/wbai/oczen：`upstream.StreamCapture`（`streamCore` 的 writeFrame 里捕 `usage` 键）
  - qodercn/qodercom/qoder/qwenwork：`streamAsOpenAI` 捕嵌套 SSE 的 usage 帧，`StreamCapture` 变体回吐
  - traework：SOLO 协议 `token_usage` 事件处回调（`streamOpts` 加 onUsage 参数）
  - qwenwork 目前渠道不可用，未做特化（其走通用 streamAsOpenAI 路径）
- **字段**：`{ts, ch, uid, model(渠道内裸名，已 strip 前缀), pt, ct, src}`；`src=upstream|none`。
- usage 帧照常透传客户端，客户端行为零变化（D7 `include_usage` 已保证上游会发）。

## 3. 积分流水（credit-ledger）与差分算法

- **记录点**：
  1. `scheduler` 签到后余额查询（`ReenableIfCredits` 旁）
  2. `app.creditTotals`（手动刷新/自动积分刷新循环，401 重试后）
- **快照**：`data/ledger/credit-snapshot.json`，key=`ch/uid` → 条目列表 `{k, r, e}`。
  非 state 文件、可随时删除——丢了只是首见账号重记一次 baseline。
- **差分规则**（只统计 `Usable=true` 条目，不可消耗池不参与）：

  | 情形 | 归因 |
  |------|------|
  | 同 key 余额上升 | earn |
  | 同 key 余额下降，到期日已过（≤今天 UTC+8） | expire |
  | 同 key 余额下降，未到期 | spend |
  | 条目消失（prev 有 cur 无） | expire |
  | 首见账号 | 只记一条「存量额度」earn baseline，**不逐条展开** |

- **key 来源**：TraeWork 用上游 `entitlement_id`（稳定唯一）；WorkBuddy 系用
  `PackageName|expireAt` 伪键；QoderCN/COM 用 `userQuota`/`addOnQuota`；qwenwork 用钱包类别。
  Qoder 系无到期时间 → 其下降恒归 spend（宁缺毋滥，不猜过期）。
- **同 key 先聚合再差分（issue #38）**：伪键可能一对多（同名同到期日的多条独立套餐），
  逐条差分会每条都对比同一份旧快照 → 一次刷新重复记 spend、快照只留末条下次继续错。
  故差分前先按 key 把 remain 求和合并成一条，保证每 key 每次刷新最多一条事件。
- **旧错误流水一次性归档（issue #38）**：升级首启把 `credit-*.jsonl` 归档为
  `old-credit-*.jsonl`（不进任何查询口径，随保留窗口到期自清），并删快照让下次刷新
  重建 baseline；marker `data/ledger/.credit-dedup-migrated` 防重复执行。
- **实测验证**（2026-09-22 冒烟）：首轮 12 账号 = 12 行 baseline；第二轮刷新无变动
  不产生流水；实时新条目（裂变包 +200）被精确捕获逐条记录。

## 4. /api/usage 响应形状

```json
{
  "recorded_since": "2026-09-22",
  "token": {
    "total": 0, "pt": 0, "ct": 0, "requests": 0,
    "by_day":  [ { "date": "09-21", "total": 0, "by_channel": {"workbuddy": 0} } ],
    "by_model": [ { "model": "glm-5.2", "channel": "workbuddy", "requests": 0, "pt": 0, "ct": 0 } ]
  },
  "credit": {
    "earn": 0, "spend": 0, "expire": 0,
    "by_account": [ { "uid": "...", "name": "...", "channel": "...", "earn": 0, "spend": 0, "expire": 0, "balance": 0 } ],
    "recent": [ { "ts": 0, "uid": "...", "name": "...", "channel": "...", "kind": "earn|spend|expire", "amount": 0, "balance": 0, "note": "..." } ]
  }
}
```

- days ∈ {1,7,30}；days=1 时 `by_day` 退化为按小时（date 形如 "14:00"）。
- `recent` 后端截 50 条倒序；昵称由 App 查 pool 状态回填（enrich 闭包）。
- ledger 未启用时返回 `{"disabled": true}`。

## 5. Web UI

- 「用量与流水」panel：4 汇总卡（Token 总量/请求数/积分消耗/积分入项）
  + 双 Tab（Token 用量：echarts 折线 + 模型表；积分流水：账号小计表 + 最近流水）
- 范围切换 今日/7日/30日；懒加载（不随 state 轮询），点刷新或切范围才拉数据
- echarts 4.3.0 走 CDN（staticfile.org），**不打包进二进制**；CDN 不可达时折线区降级为
  提示文案，表格用同一份 JSON 现渲染不受影响
- 配色语义：earn 绿 / spend 橙 / expire 红（与账号卡临期红字一致）

## 6. 配置

```json
"schedule": {
  "expiring_threshold_hours": 24
}
```

- 默认 24，normalize 钳到 ≥24（日期粒度判定低于一天无意义）。
- 影响：签到/刷新后 `ExpiringWithin` 的 horizon（pool.Pick 第一排序键的依据）。
- 注意：改大后已存的 state `expiring` 快照要等下轮余额刷新才按新口径重算。

## 7. 已知限制

1. 首启/删快照后首轮 = baseline，之前的历史无法追溯（上游不提供历史）。
2. 多端同时用同一账号会把别处的消耗算进本工具的 spend（单人工具可容忍）。
3. 差分粒度 = 两次余额刷新之间，期间的 earn+spend 相互抵消时不记（如签到 +150
   与消耗 -150 恰好同刷发生 → 无流水）；属「不追求高精确」决议内的可接受误差。
4. `by_day` 日期 key 不含年份（30 日窗口内无歧义）。
5. 数据量再涨一个量级（>50MB/月）时再考虑 rollup 偏移续扫，当前分段+按需扫描已够用。
6. 积分流水本质是「两次余额刷新间的余额变化估算」而非逐笔账：WorkBuddy 等伪键渠道
   同 key 多条套餐聚合后无法再细分到单条（issue #38 修复后的固有口径）。
