|---|---|---|---|---|---|

**跨机失败的唯一根因**：回调地址写死回环（127.0.0.1 / localhost），远端浏览器的回调打在
**用户自己机器**上，凭据到不了网关 ⇒ 只能枯等超时。【代码】各 login 包 Start 的监听与
redirect_uri 拼接；【抓包】sid 072 证明 Trae 的回调投递是纯浏览器端跳转。

## 2. 五个回环回调渠道的机制细节

### 2.1 traework（`internal/login_trae`）

- **凭据流**：授权页回调带 `authCodeInfo`（AuthCode，10 分钟有效）→ 网关持
  `CodeVerifier` + 设备公钥 POST `api.trae.cn/trae/api/v3/oauth/ExchangeToken` 换
  14 天 JWT。【抓包 sid 354/358】
- **回调形状**【抓包】：`?isRedirect=true&scope=solo&authCodeInfo={JSON}&host=...&userRegion=...&userInfo={JSON}`；
  解析器 `ParseCallback` 同时吃三形态：`refreshToken`（旧流）/ `userJwt`（兜底）/
  `authCodeInfo`（PKCE 现行）。
- **无 state 参数**：回调 URL 不携带会话标识，**回调端口是唯一会话锚点**（#170 的
  `CallbackPort` 自检据此）。
- **监听寿命 5 分钟**（Start 内 timer shutdown）；**PKCE verifier 在 state 文件**。

### 2.2 codearts（`internal/login_codearts`）

- **凭据流**：回调 `?code=...` → STS 换临时 AK/SK + SecurityToken（15 分钟凭据），
  DPoP 私钥 JWK 与 CodeVerifier 均在 Start 时生成、state 文件持久化。
- **授权 URL 由 port 参数驱动**：portal 只接受 `port`，跳转目标写死
  `http://127.0.0.1:<port>/oauth/callback`。【代码，R96③】
- **flowTTL 10 分钟**；state 逐字校验在 `applyCallback`。

### 2.3 lobsterai（`internal/login_lobsterai`）

- **凭据流**：回调 `?code=...&state=...` → 立即 `POST {apiBase}/api/auth/exchange`。
  **无 PKCE**；state（UUIDv4）是唯一防伪。
- **portal 严格只认 127.0.0.1 hostname**：改 LAN IP 的方案已被实测证伪
  （R97：portal 丢弃 redirect_uri 改发 `lobsterai://` deep-link）。
- **flowTTL 10 分钟**；回调端口可固定（`config.login.lobsterai_callback_port`，R97）。

### 2.4 qwenwork（`internal/login_qwenwork`）

- **凭据流**：PKCE + Hydra 标准流，回调 `?code=...&state=...` →
  `POST {OAuthBase}/oauth2/token`（ory_rt_ 轮换 refresh）。
- redirect_uri 注册白名单制（官方 IDE 用 `gateway.qwenwork.cn`，本工具用回环随机端口
  是实测允许的例外形态）。【代码注释 + 渠道备忘】
- **callbackTTL 5 分钟**；state 服务端只透传不校验（uuid4Hex 只做透传标识）。

### 2.5 gemini（`internal/login_gemini`）

- **凭据流**：OAuth code（**刻意无 PKCE**，参考实现协议 §2.3）→ Google token 端点换
  access/refresh。
- Google installed-app 政策：redirect host 只允许 `localhost`（**不是 127.0.0.1**，
  授权请求与 redirect_uri 必须逐字一致）。
- **flowTTL 6 分钟**；state 回调时**逐字比对**（`loginSession` 内存持有）。
- 已知坑：`localhost` 可能解析成 IPv6 `::1`，故监听器双栈绑定。【代码 callback.go 注释】

## 3. 共性结论（改造依据）

1. **回调 URL 均为「凭据自带」形状**：上游 302 把浏览器甩向回环地址时，code/authCode
   已在 URL 里；浏览器是否成功连上端口、返回 200 还是连接拒绝，上游不感知不校验。
   ⇒ **CDP 侧捕获导航 URL 即完成收集**，监听端口不再是必需品。
2. **会话防伪材料均在网关本地**：PKCE verifier / state / DPoP JWK 全部由 Start 生成并
   落 state 文件，与回调投递方式无关 ⇒ 捕获到 URL 后走既有兑换链路，零协议改动。
3. **监听器时代的四类老问题**（CDP 捕获后自动消失）：
   ① 跨机必死（根因）；② 监听寿命竞态（Trae 5min / codearts&lobster 10min）；
   ③ 随机端口的防火墙弹窗；④ localhost→IPv6 解析漂移（gemini）。
4. **人工粘贴兜底与自动回调共用同一条结论通道**：`SubmitCallbackURL` 模式
   （五渠道已全覆盖，见 §4.3）解析结果写入同一 state/session，兑换路径不分叉。
   这是回环回调渠道跨机登录的**唯一**通用解——不依赖网关机有人。

## 4. 回环回调跨机登录的定案：统一粘贴兜底（R101）

### 4.1 定案

**五渠道统一补齐人工粘贴兜底**：浏览器地址栏里打不开的那条回环回调 URL，原样粘回
面板 → 网关解析 code/凭证 → 与自动回调**同一条**兑换路径。`manualCallbackKind`
白名单五渠道：traework / codearts / lobsterai / qwenwork / gemini。

### 4.2 CDP 浏览器化：已评估、已实现、已回滚（2026-10-19）

曾完整实现过 CDP 方案（cdp.Launch 在网关机拉独立 profile 浏览器 + 被动捕获
`Network.requestWillBeSent` 回环导航 + 喂既有结论通道），实测后回滚。教训两条：

1. **CDP 只解决「人在网关机前」**：浏览器在网关机弹出，dashboard 远程、网关机
   无人值守（本工具主流部署形态）时无处可弹——对该场景无收益，反而引入
   双开/生命周期/浏览器探测复杂度。
2. **跨机类方案动手前先确认「人在哪台机器前」**：homelab 有人在网关机前的场景
   只是少数派，不能当主场景论证。

代码已全量 revert（capture.go / browserassist.go / 双开修复），无遗留。

### 4.3 五渠道粘贴入口清单

| 渠道 | SubmitCallbackURL | 状态通道 | 校验 |
|---|---|---|---|
| traework | `internal/login_trae` | login-state.json（文件） | 端口自检（CallbackPort） |
| codearts | `internal/login_codearts` | 内存 session | 端口自检 |
| lobsterai | `internal/login_lobsterai` | 内存 session | state 逐字比对 + 端口自检 |
| qwenwork | `internal/login_qwenwork` | 内存 pending | state 服务端透传不校验 |
| gemini | `internal/login_gemini` | 内存 loginSession | state 逐字比对 |

### 4.4 明确不做

- **CDP 浏览器化**：见 §4.2，回滚不复活。
- **回调改 LAN IP / 同 IP 方案**：LobsterAI 已实测证伪（R97）；Trae 虽推断可行
  （回调投递是纯浏览器端跳转）但收益与粘贴重叠，不做。
- **workbuddy/qoder 系等轮询制渠道的「兜底」**：没有 URL 回调环节，凭据靠服务端
  轮询，跨机天然通——无物可贴。
- **glm/小浣熊**：已是 CDP 读 Cookie，无 HTTP 回调，不涉及。
