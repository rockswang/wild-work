# 模型降级链定义

> 本文是「模型降级链」的**唯一权威定义**。改动 `pickModelFallback` / `fallbackWorthy` /
> 请求内重入相关代码前必读；新增 `provider.ErrKind` 时必须同步本文的归属表。
>
> 关联决议：R94（本条：降级链定义与四维处置）、R54（降级链存在与不粘滞）、R75（14018 请求内重入）、
> R38（按模型限流不得软化整号）。

---

## 1. 定义

### 1.1 一句话

**模型降级链解决的是：多账号多渠道下，某个模型临时不可用时，自动换一个能用的模型继续服务，用户不被打断。**

**它只在「换号已经用尽」时才出手——这是它和换号的分界线。**

### 1.2 完整定义（三要素）

> **降级**（Fallback）＝ 当请求的目标 `(渠道, 模型)` 已无承载能力时，
> 按用户配置的顺序，找到**另一个有承载能力的 `(渠道, 模型)`**，把请求改道过去，
> 并让下游能感知到这次改道。

三个要素缺一不可：

| 要素 | 含义 | 不满足会怎样 |
|---|---|---|
| **前提** | 目标格子**已无承载能力**（不是「这一次失败了」） | 偶发失败就降级 → 白烧备胎额度 |
| **动作** | 按配置顺序改道到另一个格子 | 随机挑 → 结果不可预期 |
| **留痕** | 下游能感知（响应头/响应体/日志/面板） | agent 不知道换了模型 → 语义错配 |

### 1.3 「降级」与相邻概念的分界

| 概念 | 是否算降级 | 为什么 |
|---|---|---|
| 换号（同渠道同模型换账号） | ❌ | 目标 `(渠道, 模型)` 没变，只是换了承载它的账号 |
| 同渠道换模型 | ✅ | 模型维度变了（§2 动作 2） |
| 跨渠道换模型 | ✅ | 模型维度变了（§2 动作 3） |
| 客户端重试 | ❌ | 不是网关的动作 |
| 原地重试同一模型（R77，workbuddyai 的 14003 单次重试） | ❌ | 目标是打同一个格子，只是再试一次 |

## 1.4 使用场景

降级链**只在这些场景生效**，其余场景不触发（见 1.5 边界）。

### 场景 1：模型饱和（14003）——核心场景

```
上游返回 429 + "Model busy. Please switch models or retry later"
```

模型整体拥塞。换号无用（每个号打这个模型都会忙），换模型立刻可用。

**这是本 PR 补上的缺口**：此前只有积分耗尽会换模型，模型饱和不会，导致首个请求必吃 429。

### 场景 2：模型额度到点（6004）

```
上游返回 429 + "quota ... will reset at 2026-10-18 11:23:28"
```

该账号在这个模型上的额度用尽（重置点在未来）。换号可能有效（别的号还有额度），
所以**先换号**；全部号都撞了才换模型。

### 场景 3：积分耗尽（14018）

```
上游返回 429 + code 14018
```

账号的积分池空了。多账号渠道先换号；单账号渠道该账号对该模型彻底不可用 → 换模型（R60）。

### 场景 4：整渠道全灭

某渠道所有账号都被禁用/冷却（例如全部登录态失效）。此时 `modelHasCapacity` 对任何模型
都返回 false，入口降级会直接跨渠道。

### 不适用场景（明确排除）

| 场景 | 为什么不降级 |
|---|---|
| 内容被拦截（`ErrContentBlocked`） | 换模型也会被拦，白烧额度 |
| 上下文超长（`ErrPromptTooLong`） | 换模型治不了，应让客户端缩上下文 |
| 参数错误（`ErrBadParams`） | 同上 |
| 图片无效（`ErrImageInvalid`） | 同上 |
| 登录态失效（`ErrSessionDead`） | 换模型治不了，应重新登录 |
| 5xx 上游故障（`ErrServer`） | 换模型治不了本，且可能污染更多渠道 |
| WAF 拦截（`ErrWafBlock`） | 上游已给确定性结论 |
| 该号无此模型（`ErrModelBlocked`） | 上游已给确定性结论 |

## 1.5 功能边界

### 边界 1：不解决「账号坏」，只解决「模型不可用」

换号是前置阶段（§2 动作 1）。账号级问题在换号阶段就该被消化掉。

### 边界 2：一次请求最多降级一次

`fbAttempt == 0` 硬关卡。备胎再失败就透传**最后一次真实上游错误**，不递归。
理由：链式降级（A→B→C）会让延迟与额度消耗不可控，且难以归因。

### 边界 3：不改变请求内容，只改 `model` 字段

降级只做两件事：改写 body 的 `model`、重新注入思考强度（`applyEffort`）。
不动 prompt、不动 tools、不动其他参数。**内容类错误因此不可能靠降级解决。**

### 边界 4：不粘滞，每次请求重新判定

没有记忆，没有粘滞窗口。上游一解冻，下一个请求立刻切回原模型（R54）。
代价是每个请求都要做一次容量探测（未配置规则时零开销，见边界 6）。

### 边界 5：单账号渠道不参与请求内重入

`SingleAccount` 渠道（oczen / kilo）唯一账号不可重登，任何惩罚都等于整条渠道下线。
429 原样透传，让客户端按 `Retry-After` 退避。

### 边界 6：未配置降级链 = 零开销

`len(rules) == 0` 直接返回，连容量探测都不做。正常路由不受任何影响。

### 边界 7：流式已写出的请求无法降级

触发条件含「尚未写过任何响应字节」。一旦开始向客户端写 SSE，中途失败无法改道。

### 边界 8：无法区分账号级限流与模型级饱和

这是 §3 顺序消解策略的固有代价。traework/qwenwork/qodercn/qodercom 把任意 429
都归 `ErrSoftRate`，因此账号级限流也会走到换模型。**可能多烧一份备胎额度**，
这是刻意接受的权衡（比让客户端直接失败更友好）。

### 边界 9：只在「入口」和「轮转耗尽」两个点触发

不存在第三种触发点。轮转过程中不会因为单次 429 就换模型——必须把所有账号试完。

## 2. 降级链不是什么

先把三个容易混的动作分开，**它们不是一回事**：

| # | 动作 | 渠道 | 模型 | 账号 | 用户感知 | 成本 |
|---|---|---|---|---|---|---|
| 1 | **换号**（Rotation） | 同 | **同** | **变** | 完全无感 | 零（同渠道内换） |
| 2 | **同渠道换模型** | 同 | **变** | 同批 | 响应 `model` 变了 | 低（同渠道另一模型的额度） |
| 3 | **跨渠道换模型** | **变** | **变** | 不同批 | 响应 `model` 变了 | 高（别的渠道额度） |

**降级链 = 动作 2 + 动作 3**，即「模型维度的替换」，两种变体都属于它。

**动作 1（换号）不属于降级链**，它是降级链的**前置阶段**。

### 为什么动作 2 和 3 是同一件事的两种变体

它们的本质相同：**当前 `(渠道, 模型)` 这个格子没容量了，换一个格子。** 区别只在「换多远」：

- **入口降级**时，我们已确认「这个模型在本渠道全冷」→ 就近换同渠道兄弟模型（动作 2）成本最低
- **请求内重入**时，我们只知道「刚撞了 429」，不知道是账号级还是模型级 → 必须远离同批账号（动作 3）

「跨不跨渠道」不是分类依据，而是**信息完备度决定的实现细节**。详见 §6。

### 为什么换号必须排在前面

如果一上来就换模型，会白烧备胎额度——而大多数失败其实换个号就好了。

```
先换号（便宜）→ 换遍了还不行 → 才换模型（贵）
```

---

## 3. 为什么「ErrSoftRate 一个值代表两种含义」不是 bug

429 软限流既可能是「你这个号被限了」，也可能是「这个模型满了」。分类的时候分不清。

**这是刻意接受的，因为不需要分清：**

- 换号是最便宜的动作（同渠道、不花别的渠道的钱）
- 如果真是号的问题 → 换号就解决了，根本走不到换模型
- 如果换遍所有号还是 429 → 那就一定不是单个号的问题 → 这时候才值得付换模型的代价

**用「先换号、耗尽才换模型」这个顺序，把二义性消化掉了。** 这是成本递进的判定策略，不是分类缺陷。

> ⚠️ 这个策略有一个明确的边界：**它无法区分「账号级限流」和「模型级饱和」**。
> 代价见 §7 已知限制第 1 条。

## 4. 第一性原则：三个维度，一种处置

**核心一句**：先搞清楚失败是谁的问题，再在同一个维度里换东西。**跨维度替换一律禁止。**

| 维度 | 判据 | 允许的处置 | 明确禁止 |
|---|---|---|---|
| **账号** | 该账号不可用，同渠道其他账号可能可用 | 换号（`MaxRotate` 封顶）；上表 `account-rotate` | 不许跳过换号直接换模型 |
| **模型** | 该渠道对**该模型**已无承载能力（模型全冷 / 整渠道全灭） | 换模型（同渠道或跨渠道，见 §2） | 不许原地无限重试 |
| **请求** | 错误跟着请求体走，换谁都会一样失败 | 原样透传，什么都不做 | 不许换号、不许换模型、不许冷却 |

**「无承载能力」的精确定义**（`modelHasCapacity`）：遍历渠道内全部账号，若存在至少一个账号满足
「未禁用 && 未整号冷却 && 该模型未在该账号的模型级冷却中」，则有容量。

### 四类处置动作（实现视角）

上表三个维度落成代码时展开为四类，因为「账号维度」有两种相反的处置：

| 处置类 | 换号 | 冷却 | 换模型 | 什么时候用 |
|---|---|---|---|---|
| `request` | ❌ | ❌ | ❌ | 错误随请求体走，换谁都会复现 |
| `account-transparent` | ❌ | ✅ | ❌ | 上游已给确定性结论，换号只会再撞一次 |
| `account-rotate` | ✅ | ✅ | ❌ | 账号问题，换号有价值 |
| `model` | ✅ | ✅ | ✅ | 该渠道对该模型无承载能力 |

## 5. 错误类型全量归属表

新增 `provider.ErrKind` 时必须在此表补一行，否则不变量测试
（`internal/server/fallback_dimension_test.go`）会失败。

四类处置（按「动作幅度」排序）：

| 处置类 | 换号 | 冷却 | 换模型 | 含义 |
|---|---|---|---|---|
| **request** | ❌ | ❌ | ❌ | 请求自身的问题，换谁都会复现 → 零动作，原文透传 |
| **account-transparent** | ❌ | ✅ 软冷却 | ❌ | 上游已给确定性结论（WAF/该号无此模型），换号只会再撞一次 → 冷却该号 + 立即透传 |
| **account-rotate** | ✅ | ✅ | ❌ | 账号可用性问题，换号有价值 → 换号；换模型治不了本 |
| **model** | ✅ | ✅ 模型级 | ✅ | 本渠道对该模型无承载能力 → 换号耗尽后换模型 |

| ErrKind | 处置类 | 具体动作 |
|---|---|---|
| `ErrHardCredit` | **model** | 多账号：整号硬冷却（可截到发奖窗口）；单账号：**模型级**冷却（R60）。换号耗尽后可换模型 |
| `ErrSoftRate` | **model** | 模型级冷却（6004 按重置点，否则 `SoftCooldown`）；同号第二个模型也撞则升级整号（粒度变、时长不延长）。换号耗尽后可换模型 |
| `ErrSessionDead` | account-rotate | 标记 `SessionDead`（不 `Disable`，R76）；换号 |
| `ErrNotFound` | account-rotate | 软冷却（不累计 `errCount`）；换号 |
| `ErrServer` | account-rotate | 计错冷却（渠道可声明 `NoCooldownOnServerError` 豁免）；换号 |
| `ErrClient` | account-rotate | **不计错**（错误跟请求体走），仅轮转以兼容同模型不同账号的权益差异 |
| `ErrAccountFault` | account-rotate | 软冷却；换号 |
| `ErrWafBlock` | **account-transparent** | 软冷却；**立即透传，不换号** |
| `ErrModelBlocked` | **account-transparent** | 软冷却；**立即透传，不换号** |
| `ErrContentBlocked` | request | 无动作，透传 |
| `ErrPromptTooLong` | request | 无动作，透传 |
| `ErrImageInvalid` | request | 无动作，透传 |
| `ErrBadParams` | request | 无动作，透传 |
| `ErrPassthrough` | request | 无动作，透传 |
| `ErrNone` | —（成功） | 无 |

**「可换模型」的判定依据**：`fallbackWorthy(kind)` = `ErrHardCredit || ErrSoftRate`。
其余错误即使换号耗尽也不换模型——内容类换模型必然复现，5xx/登录态换模型治不了本，
WAF/无此模型是上游给的确定性结论。

> ⚠️ **`ErrWafBlock` / `ErrModelBlocked` 的易错点**：两者的 `ErrKind` 注释含「账号级」字样，
> 容易被误认为可换号。实际 `Rotatable()` 返回 `false`，handler 在
> `case provider.ErrWafBlock, provider.ErrAccountFault, provider.ErrModelBlocked` 分支里
> **冷却后立即 `transparentError` 返回**（`ErrAccountFault` 除外）。即「罚这个号，但不换号」。
> 本表以**代码实际行为**为准，不以注释文字为准。

## 6. 两条触发路径

### 路径 A：入口降级（请求进入时）

**触发条件**：请求模型在本渠道 `modelHasCapacity == false`（模型全冷 / 整渠道全灭）。

**是否允许同渠道备胎**：✅ 允许（`skipSameChannel=false`）。

理由：此时「该模型在本渠道已全冷」是**已知事实**。上游配额按模型计，同渠道的兄弟模型是另一个
`(账号, 模型)` 格子，换它正是降级链配置的本意。

### 路径 B：请求内重入（轮转耗尽后）

**触发条件**（全真）：
1. `fbAttempt == 0`（一次客户端请求最多降级一次）
2. `fallbackWorthy(lastKind)` 为真
3. 非单账号渠道（`!rt.SingleAccount`）
4. 尚未写过任何响应字节（轮转失败路径天然成立）

**是否允许同渠道备胎**：❌ 禁止（`skipSameChannel=true`）。

理由：
- 同渠道兄弟模型走**同一批账号**。若本轮 429 实为账号级限流
  （traework/qwenwork/qodercn/qodercom 等渠道把任意 429 都归 `ErrSoftRate`），
  重打一遍必然二次撞墙。
- 更糟的是：该账号第二个模型也撞墙后，pool 会把「模型级冷却」升级为「账号级冷却」——
  **冷却时长取已有条目的最晚到期时刻（不延长），但粒度变了：可用容量从「1 个模型格子」
  缩到「0，整号对所有模型下线」**。
- 宁可把真实的 429 透传给客户端，也不拿同一批账号再撞一次。

### 为什么两条路径的 `skipSameChannel` 不同

**不是特例，而是同一条规则在信息完备度不同时的自然结果：**

| 场景 | 我们知道什么 | 是否允许同渠道备胎 |
|---|---|---|
| 入口降级 | 「该模型在本渠道已全冷」是**已知事实** | ✅ 允许 |
| 请求内重入 | 只知道「刚撞了 429」，**不知道是账号级还是模型级** | ❌ 禁止 |

## 7. 三条硬规则

### 规则 1：顺序消解（成本递进）
先按账号维度试（便宜），耗尽才升级到模型维度（贵）。见 §3。

### 规则 2：降级不递归
一次客户端请求最多降级一次（`fbAttempt` 封顶）。备胎再失败就透传**最后一次真实上游错误**
（不是包装成 503），客户端才能看到 6004 重置时间等上游细节。

### 规则 3：降级必留痕
- 响应头 `X-Model-Fallback: 原模型 -> 备胎`（仅在降级成功路径发出，透传时不得残留）
- 响应体 `model` 字段写备胎全路径
- app.log 一行 `model fallback platform=X from=Y to=Z`
- 面板「降级记录」区块（`NoteFallback` 事件）

**记账归实际执行者**：token 流水（`ledger.AppendUsage`）/ 请求日志（`statRow.Model`）/
今日模型消耗（`stats.AddUsage`）三面一致，都记备胎。

**恢复探针**：`pickModelFallback` 第二返回值 `primaryAvail` = 「原模型此刻有可用账号」，
仅用于关闭降级事件。不能用「未降级」代替——那会把「原模型仍全冷但备胎也没容量」谎报成已恢复。

## 8. 已知限制（如实披露）

1. **账号级 429 也会触发换模型**：traework/qwenwork/qodercn/qodercom 把任意 429 都归
   `ErrSoftRate`，无法在分类层区分账号级与模型级。代价是可能多烧一份备胎额度。
   这是刻意接受的权衡——比让客户端直接失败更友好。
2. **单账号渠道豁免**：`SingleAccount` 渠道（oczen / kilo）唯一账号不可重登，任何惩罚都等于
   整条渠道下线，故不参与请求内重入，429 原样透传（`R16` / 不变量 22）。
3. **流式已写出的场景不补救**：触发条件含「尚未写过任何响应字节」，中途失败无法降级。
4. **不粘滞**：每个请求都按原模型重新判定，上游解冻即自动切回（R54）。
5. **未配置规则时零开销**：`len(rules) == 0` 直接返回，不做容量探测。代价是删规则后
   残留的进行中降级事件不会自动关闭（环形 200 条自然淘汰，重启即清）。
6. **生产端到端未自然复现**：14003 窗口较难遇到，行为由单测锁定；下次真实饱和时看
   app.log 同请求的 `model fallback platform=` 行即自证。
