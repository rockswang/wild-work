# 三接口协议兼容改造备忘

> 目标：把本项目唯一的 OpenAI Chat Completions 接口，扩展为 **Chat Completions + OpenAI Responses + Anthropic Messages** 三接口兼容，
> 使 `codex` CLI、`claude` CLI 等官方 agent 客户端可直接接入。
>
> 状态：**已实施并端到端验证通过**（v2.1.0 之后）。

---

## 1. 缘起与调研

调研对象：`ref/tokligence-gateway`（Apache-2.0，Go，commit `44b3acd`）。
它用「统一中间表示 = OpenAI Chat Completions」把三种前端协议降维到同一个执行内核，
思路与本项目 `provider.Upstream.ChatStream(a, body) → 上游 OpenAI SSE` 的语义完全吻合。

**仅借鉴算法与事件序列，未复制代码**——其源码风格（`interface{}` 泛用、单文件 1000+ 行、
`fmt.Printf` 调试残留）不符合本仓库约定，且其实现本身存在三处规范瑕疵（见 §5）。

调研得到的两个关键判断：

1. **两套 Anthropic 桥是冗余的**（`internal/httpserver/anthropic` 与 `internal/translation/adapter`），
   其中 `ConvertOpenAIStreamToAnthropic` 的三个问题（tool_use 不增量、stop_reason 硬编码、
   usage 瞎猜）必须在移植时修掉。
2. **`buildResponsesResponseFromChat` 不合规**：把 `type:tool_call` 塞进 `message.content`，
   而官方规范要求 `function_call` 是**独立 output item**（带 `call_id`）。Codex CLI 不认前者。
   这是移植时最容易踩的坑——直接照搬会得到「能返回内容但工具调用全部失效」的假兼容。

## 2. 架构决策：两层结构

### 决策

不改动 `internal/server` 主链路，在其上叠一层边缘兼容层（`internal/gateway`），
通过 **in-process 调用**（`io.Pipe` + `net/http` 形状的 ResponseWriter）复用内层 handler。

```
客户端
  │
  ├─ POST /v1/chat/completions ──┐  （直通内层，调用栈与旧版完全一致）
  ├─ POST /v1/responses ─────────┤
  ├─ POST /v1/messages ──────────┤
  ├─ POST /v1/messages/count_tokens
  │                              ▼
  │      ┌── internal/gateway（新增，~1900 行）────────────────┐
  │      │ ① 鉴权转接：x-api-key / Bearer → 统一校验            │
  │      │ ② 模型路由：裸名 → channel/model（Router）           │
  │      │ ③ 协议转换：Responses/Anthropic 请求 → Chat JSON     │
  │      │ ④ in-process callChat：pipeRW → 内层 handler         │
  │      │ ⑤ 协议转换：Chat SSE/JSON → Responses/Anthropic      │
  │      └────────────────────┬───────────────────────────────┘
  │                           │ io.Pipe（非 HTTP 自环）
  │      ┌────────────────────▼───────────────────────────────┐
  └─────►│ internal/server.Handler —— 零改动（仅加 2 个访问器）│
         │  粘性路由 · NeedsRefresh · MaxRotate 重试 · Classify │
         │  → provider.Upstream.ChatStream → Stream/Aggregate   │
         │  /v1/chat/completions · /v1/models · /status ·              │
         │  /healthz · /api/* · Web UI                          │
         └──────────────────────────────────────────────────────┘
```

### 为什么不用 HTTP 自环

`http.Post("http://127.0.0.1:7863/v1/chat/completions")` 会引入一串问题：
`0.0.0.0`/`::` 监听地址无法作为目标、鉴权双份校验、HTTP client 超时与端口未监听的启动竞态、
连接数翻倍。`io.Pipe` 方案零网络开销、零配置依赖，且 `io.Pipe` 无缓冲，
**每次 Write 都阻塞到读端消费**，天然具备「写即送达」语义，无需模拟 `Flush`。

### 与「内联 execChat」方案的量化对比

| 维度 | 内联执行层重构 | 边缘兼容层（**已采用**） |
|------|---------------|----------------------|
| 新增代码 | ~1550 行 | ~1900 行 |
| 改动现有代码 | ~200 行（含主链路抽取） | ~15 行（3 处：接口签名 2 处 + 访问器 1 处） |
| 主链路回归风险 | 中 | 低 |
| 可测试性 | 需构造 pool/upstream | 可脱离 pool 单测（喂假 Chat SSE 断言事件序列） |

结论：代码量多 20%，但改动面小一个数量级。本项目是单机个人工具、无统一埋点需求，
**架构清晰度与低回归风险的价值高于代码量**。

## 3. 实施顺序与实际产出

### P0 · 并发串号修复（前置，独立可交付）

**发现的缺陷**：`qoder.Client` 用实例字段 `lastModel` 记录「上次请求的模型名」，
`ChatStream` 写入、`Stream`/`Aggregate` 再读出——两次调用之间是竞态窗口。
`Client` 是 `main` 里的单例，多账号并发时 A 的响应会带上 B 的模型名。

**同类缺陷**（一处修复全部覆盖）：

| 渠道 | 原状 | 后果 |
|------|------|------|
| qoder | 读全局 `lastModel` | 并发串号 |
| traework | 流式/聚合里 model 硬编码 `""` | 客户端永远拿到空模型名 |
| workbuddy / wbai | 透传上游 chunk 的 model | 返回上游裸名（`glm-5.2`）而非请求名 |

**修复**：把 model 从「渠道内部状态」变成「调用方入参」——

```go
// provider.Upstream
Stream(w http.ResponseWriter, r io.Reader, model string) error
Aggregate(r io.Reader, model string) (map[string]any, error)
```

改动 7 处（4 个实现 + 2 个调用点 + 1 个 fake），删除 qoder 的 `lastModel/lastModelMu`。
`handler.go` 传入**客户端请求的原始模型名（含前缀）**而非剥前缀后的裸名。

副产品：这是三接口改造的必要前置——Responses 与 Anthropic 都必须回填客户端原始模型名
（客户端用它做会话 key），旧签名下做不到。

**回归测试**：`internal/server/handler_model_isolation_test.go`
（32 goroutine 并发不同模型，断言响应不串号；已验证「回退修复必失败」的灵敏度）。

> 注：本机无 gcc，`go test -race` 不可用；测试通过 `-count=10` 与人工回退验证灵敏度。

### P1 · 兼容层骨架

- `pipe.go` — `pipeRW` + status 握手（buffered channel + `sync.Once`，保证「显式 WriteHeader 优先于隐式 200」）
  + `innerResult`（含 `Close`/`ReadAll`）
- `gateway.go` — `Gateway` 主入口、鉴权（两种头）、`Routes` 注册
- `router.go` — 模型名解析（前缀 → map 精确 → map 通配 → default → 报错）
- `errors.go` — 两种协议的错误体形状 + SSE 写入工具
- `chat_sse.go` — 共用 SSE 迭代器 + `toolCallAccumulator`（按 index 合并增量 tool_calls）
- `util.go` — 宽容取值工具（三接口字段类型在客户端间不统一，走宽容取值而非严格结构体）

### P2 · Responses 接口

- **请求**：`input`（string / 数组，元素支持 message / function_call_output / reasoning）、
  `instructions` → system、扁平 `tools` → 嵌套、`text.format` → `response_format`、
  `reasoning.effort` → `reasoning_effort`、`max_output_tokens`/`max_completion_tokens`/`max_tokens` 三别名
- **非流式**：`output` 数组由 `message` item 与**独立 `function_call` item** 组成；`output_text` 便利字段；`usage` 字段名映射
- **流式**：严格事件序列（`response.created` → `in_progress` → item/content_part/`output_text.delta` → 各级 done → `completed` → `[DONE]`）
- **明确拒绝**：`previous_response_id`（无状态实现，返回 400 并提示把历史放进 `input`）
- **容忍忽略**（记日志）：`store` / `include` / `truncation` / `metadata` / `background`

### P3 · Anthropic 接口

- **请求**：`system`（string / blocks）、user `tool_result` → 独立 `role=tool` 消息、
  assistant `tool_use` → `tool_calls`、`input_schema` → `function.parameters`、
  `tool_choice`（auto/any/tool/none → auto/required/function/none）、`image`（url 与 base64 两种 source）
- **流式**：块按 index 递增成对出现；**thinking 块 index 0、text 块 1、tool 块从 2 起**
- **`count_tokens`**：本地启发式（CJK 1 字 ≈ 1 token，其余 4 字符 ≈ 1 token），Claude Code 必需

### P4 · 集成与文档

`config.json` 新增 `compat` 段；`cmd/wild-work/main.go` 装配外层 mux；
`internal/app` 增加 `SetRootHandler` 与 `serveHandler`（`httpRoot` 与内层 `handler` 分离，
保留 `handler.*` 的强类型访问：`SetAPIKey`/`ChannelModels`/`InvalidateModels`）。

## 4. 关键不变量（改动前必读）

1. **`internal/server` 主链路保持可用且不被绕过**：`POST /v1/chat/completions` 与 `GET /v1/models`
   由内层直接服务，兼容层不介入。
2. **兼容层通过 `Gateway.call()` 唯一入口访问内层**，不得再引入第二次网络跳转。
3. **`pipeRW.Flush()` 是空操作**——这是 `io.Pipe` 无缓冲语义决定的，不要「优化」成缓冲 + 定时 flush。
4. **status 握手必须保留 `sync.Once`**：内层可能「先 WriteHeader(err) 再写错误体」，
   也可能完全不写（此时补 200），两种路径都不能让调用方永久阻塞。
5. **调用方读完必须 `res.Close()`**，否则内层 goroutine 可能阻塞在 `Write` 上造成泄漏。
6. **Responses 的 `function_call` 必须是独立 output item**，带 `call_id`；
   不得退回「塞进 message.content」的写法（Codex CLI 不认）。
7. **Anthropic 的 tool_use 参数必须走 `input_json_delta`**，`content_block_start` 里
   `input` 固定为 `{}`；在 start 里一次性给完整 input 会让等待 partial_json 的客户端卡住。
8. **块 index 必须递增且 start/stop 成对**；thinking(0) → text(1) → tool(2..)，关闭前一个才能开下一个。
9. **模型名回填成客户端请求名**，不是上游返回名（`Provider.Upstream.Stream/Aggregate` 的 model 参数）。
10. **零 token**：兼容层不做 token 日志；`count_tokens` 只算字符不输出内容。

## 5. 与参考实现的差异（有意修正）

| 项 | tokligence-gateway | 本项目 |
|----|-------------------|--------|
| Responses 工具调用 | 塞进 `message.content`（`type:tool_call`） | 独立 `function_call` output item（带 `call_id`） |
| Anthropic tool_use 流式 | 结束时一次性 `content_block_start`+`stop`，无 delta | `input_json_delta` 增量下发 |
| Anthropic stop_reason | 恒为 `end_turn` | 按 finish_reason 映射（`length`→`max_tokens`、`tool_calls`→`tool_use`） |
| Anthropic usage | `output_tokens=len(text)/4`、`input_tokens=0` | 上游真实值 |
| 思考链 | 无映射 | `reasoning_content` → `thinking` 块（流式 `thinking_delta`） |
| 会话状态 | 服务端 session + `submit_tool_outputs` | 完全无状态（`previous_response_id` 明确拒绝） |
| 执行内核 | `adapter.ChatAdapter` + ledger/userstore/firewall | 复用本项目 `provider.Upstream` + pool/scheduler |

## 6.1 下游 agent 实机嗅探与缺陷修复（v2.2.1）

### 嗅探方法

用「本地记录代理 + 真实官方 CLI」验证兼容层：

1. `temp/sniff_proxy.py` 在 `127.0.0.1:7899` 记录下游客户端发往网关的**原始请求体**，再转发到真实网关；
2. 把 `codex` 的 `base_url` 指向代理，跑 `codex exec --json`；
3. 直接断言网关请求体，绕开「猜客户端发什么」的误差。

### 发现的缺陷：`function_call` 输入项被丢弃

**现象**：Codex CLI 首轮工具调用正常，**第二轮必失败**：

```
{"error":{"code":"upstream_error","message":"tool calls and tool results do not match, please start a new conversation and retry"}}
```

**根因**（对比真实 payload 与转换结果）：

Codex 每轮回填时，把上一轮的 `function_call` item **原样回传**，再追加 `function_call_output`：

```json
[{"role":"user", ...},
 {"type":"function_call","call_id":"call_...","name":"shell_command","arguments":"{...}"},
 {"type":"function_call_output","call_id":"call_...","output":"..."}]
```

而 `convertResponsesItems` 只处理 `function_call_output` → `role=tool`，把 `function_call` 当作
「无 role 的未知 item」记日志丢弃，于是 `role=tool` 变成**没有宿主 assistant.tool_calls 的孤儿消息**。
上游校验工具调用序列时直接报错（WorkBuddy 国际版为 `11148 tool_call_sequence_broken`）。

**修复**（`internal/gateway/responses.go`）：新增 `function_call` 分支，还原为 `assistant.tool_calls`；
连续多个 `function_call`（并行工具调用）合并进同一条 assistant 消息。缺 `call_id` 时显式报错，
不静默产生坏序列。

> 该缺陷对「只发一轮工具调用」的自测脚本不可见——必须用**真实多轮 agent** 才能暴露，
> 这也是本次用官方 CLI 而非自写脚本验证的价值所在。

### 复验（v2.2.1，本地实例 `127.0.0.1:7863`，凭据取自 `temp/auths`）

构建：`go build ./... && go vet ./... && go test ./...` 全绿后
`GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -ldflags "-H windowsgui" -o dist/wild-work.exe ./cmd/wild-work`。

| 用例 | 修复前 | 修复后 |
|------|--------|--------|
| 回放 Codex 真实首轮 payload | ✅ 200 + `function_call` | ✅ |
| 回放 Codex 真实**回填轮** payload | ❌ 400 `tool_call_sequence_broken` | ✅ 200 + `message` |
| `codex exec` 实机多轮工具循环（4 次工具调用） | ❌ 第二轮中断 | ✅ 循环完整跑完 |
| `claude -p --allowedTools Read` 实机工具闭环 | ✅ | ✅ 返回 `ZQ-42` |
| 协议级多轮套件（三接口 × 流式/非流式/工具回填） | — | ✅ 17/17 |
| 跨渠道套件（四渠道 × 三接口 + 思考块 + 边界） | — | ✅ 15/17（2 项为环境问题，见下） |

### 验证环境限制（非网关缺陷）

| 现象 | 结论 |
|------|------|
| `qoder/*` 在本地实例上 502 / 超时 | 本机到 `openapi.qoder.com.cn`、`gateway.qoder.com.cn` 直连与走代理均返回 **503**，属环境网络阻断；同一凭据在外部机器（`10.127.127.10`）上正常 |
| `traework/kimi-k3` 首次请求 173.9s | 上游首轮冷启动慢（后续同模型 20.7s，`DeepSeek-V4-Pro` 3.4s）；非兼容层问题，客户端需设置足够超时 |

### 顺带确认的三接口差异（非缺陷，但需知晓）

| 项 | Chat（内层） | Responses / Anthropic（兼容层） |
|----|-------------|------------------------------|
| 裸模型名 | **强制** `channel/` 前缀，否则 400 | 按 `compat.default_channel` 兜底 |

即：`compat` 路由只对兼容层生效，Chat 主链路不受影响（符合 R12 主链路零改动原则）。

## 8. 后续可选增强

- **`GET /v1/responses/{id}`**：当前不支持（无状态）。若要支持需引入响应存储。
- **`stream_options.include_usage`**：Anthropic 侧 usage 已在下游汇总，Chat 侧透传即可。
- **细粒度 `count_tokens`**：接入真实 tokenizer（如 tiktoken 的 Go 实现）可显著提升精度，当前为启发式。
- **模型能力感知路由**：`provider.ModelInfo` 已支持 `SupportsImages`，可据此在路由层拒绝不支持图片的渠道。
